the gate

A separate process decides when work is done.

The verifier is not another model opinion. It runs the command your project already trusts and reads the exit code.

Checks run outside

The engine edits files and runs commands. The verifier runs pytest, the build, or lint in a separate subprocess. A model cannot mark its own work as passing.

Every step has a checkpoint

Each step starts from a git ref under refs/maxcode/. A failed attempt rolls back to that ref, not to a half-edited tree.

Cost per finished task

Every run records input and output tokens. Missing usage or pricing is reported as partial, never guessed. A dollar cap can stop the run.

the loop

Plan, work, verify, checkpoint.

01

Plan

The planner splits the task into small, ordered steps and names the checks for each one.

02

Work

The worker edits one step through the engine. It never receives the final score command.

03

Verify

The verifier runs the checks. A failure returns the output to the worker and retries from the checkpoint.

04

Done

Only a clean check run closes the step. No checks means unverified, not done.

benchmark

One run. Two verifier arms.

Three pinned projects, the same final score command, and the raw logs committed next to the result. The honest result is a 0-point gain.

The verifier-on arm hit the 300-second worker timeout before verification; the repositories were unchanged, so the score still passed. This is a ceiling effect, not evidence of an advantage.
