## Provider config

maxcode reads `maxcode.toml` from the current directory, a `--config` path, or
the user config directory. The key is read from the environment variable named
by `api_key_env`; it is never written to a config file or run log.

```toml
[provider.main]
base_url    = "https://your-provider.example/v1"
api_key_env = "MAXCODE_API_KEY"

[planner]
provider = "main"
model    = "your-planner-model"

[worker]
provider = "main"
model    = "your-worker-model"
```

The engine side uses the Responses API. Codex 0.165 removed Chat Completions
support, so the endpoint must expose `/v1/responses`.

## Ollama

Ollama 0.31.1 works with the adapter when the worker command disables web
search and multi-agent tools. The adapter does this by default. A working
worker config, with the hosted planner used in the live demo:

```toml
[provider.pollinations]
base_url    = "https://text.pollinations.ai/openai"
api_key_env = "POLLINATIONS_KEY"

[provider.local]
base_url    = "http://127.0.0.1:11434/v1"
api_key_env = "OLLAMA_API_KEY"

[planner]
provider = "pollinations"
model    = "openai"

[worker]
provider = "local"
model    = "qwen2.5:3b"
```

Set `OLLAMA_API_KEY=local`; Ollama ignores the value. The adapter reads
`MAXCODE_REASONING_EFFORT` (default `low`) and
`MAXCODE_MODEL_CONTEXT_WINDOW` (optional). The live runs used `none` and
`16384`.

A local 3B planner is not reliable enough: on 2026-11-01 `qwen2.5:3b` failed
the plan schema, and `llama3.2:3b` proposed editing tests. The probes are in
`docs/BENCH.md`.

## Engine selection

The adapter looks for an engine in this order:

1. `MAXCODE_ENGINE_BIN`
2. `maxcode-engine` on `PATH`
3. `codex` on `PATH`, version 0.165 or newer

Stock Codex and `maxcode-engine` produced the same event types on the same live
task. The fork is optional; use it only if you need the rebranded binary or a
future engine patch.

## Credentials

Never commit a key. maxcode redacts provider errors and writes only token counts
to the JSONL run log. A missing key fails before any request.
